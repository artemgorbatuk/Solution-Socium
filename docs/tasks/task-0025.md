**Описание:**

Create / rename / delete чата сразу отражаются в сайдбаре у всех подключённых клиентов (SignalR), по тому же принципу, что комнаты в [task-0020](task-0020.md): патч локального списка чатов комнаты без полной перезагрузки с сервера. Права доступа не меняем — [Решения разработчика](#решения-разработчика).

**Функциональные требования:**

1. Rename: сменили название — у остальных в списке чатов комнаты сразу новое имя — [Сценарий](#сценарий), [Frontend](#frontend).
2. Create (ручной): новый чат появляется в списке у всех онлайн, у кого комната уже раскрыта (список смонтирован) — [Сценарий](#сценарий).
3. Delete: чат исчезает из списка у всех онлайн (раскрытая комната) — [Сценарий](#сценарий).
4. Без полного reload: клиент **патчит** локальный массив чатов комнаты (добавить / сменить name / убрать), не вызывает GET `/api/chat?roomId=` на каждое событие — [Frontend](#frontend).
5. Права: кто может create/update/delete — как сейчас ([task-0021](task-0021.md)); `chatListUpdated` (превью/unread) не смешивать с этим событием — [Realtime](#realtime).

**Технические требования:**

1. Аудитория: **все** подключённые к хабу (broadcast), как `roomChanged` — [Realtime](#realtime).
2. Domain event **после** успешного `SaveChanges` в `ServiceChat` (create / update / delete): `ChatChangedEvent` с видом операции — [События](#события). Существующий `ChatCreated` **до** Save ([task-0022](task-0022.md), Participant Stage) для UI **не** использовать.
3. Авточат при создании комнаты ([task-0019](task-0019.md)): появляется через GET при expand комнаты (as-is); отдельный `ChatChanged` на авточат в этом срезе **не** слать — [Решения разработчика](#решения-разработчика).
4. Handler тонкий → `IChatNotifyPort` → Realtime; объекты события и payload — только через `ChatMapper` в локальную переменную (rule-0003 п. 31, 44–45; [AGENTS.md](../../AGENTS.md)).
5. SignalR: клиентское событие `chatChanged`; на `IChatConnection` — `SendToAllAsync` — [Realtime](#realtime).
6. Payload: `kind` (`created` / `updated` / `deleted`), `roomId`, `chatId`, `name?` — [Realtime](#realtime).
7. Frontend: подписка в `RoomChats` (не в корневом Sidebar — чаты живут там); патч списка; у инициатора убрать `loadChats` / `ChatChanges.notify` там, где заменяет событие — [Frontend](#frontend).
8. Тесты: mapper; FE-патч create/rename/delete; ServiceChat/ChatApi регрессия; runbook realtime.

### Решения разработчика

| Вопрос | Решение |
|--------|---------|
| Кому слать | Всем подключённым к хабу (broadcast), как `roomChanged` |
| Объём | Create + rename + delete **ручного** чата |
| Связка | Domain event после `SaveChanges` → handler → notify |
| `ChatCreated` (0022) | До SaveChanges без изменений; для UI **не** использовать |
| Авточат (0019) | Без `ChatChanged` в этом срезе; список при expand → GET |
| Модель | `ChatChangedEvent` + `ChatChangedKind` Created/Updated/Deleted |
| Payload | `kind`, `roomId`, `chatId`, `name?` |
| Создание объектов | Только Mapper → локальная переменная → вызов |
| FE | Патч в `RoomChats`; не GET списка на каждое событие |
| Инициатор | Патч по `chatChanged` (вместо `loadChats` / `ChatChanges` на CRUD чата) |
| `chatListUpdated` | Оставить для превью/unread; не расширять под add/remove чата |
| Права | Не менять |

### Сценарий

1. Пользователь A создаёт / переименовывает / удаляет чат (HTTP).
2. После успешного commit в БД все онлайн-клиенты получают SignalR `chatChanged`.
3. У клиентов с раскрытой комнатой `RoomChats` патчит строку чата; полный список с API не запрашивается.
4. У клиентов с свёрнутой комнатой событие можно игнорировать до expand (тогда как сейчас — GET).

### As-is

```text
ServiceChat.Create/Update/Delete → SaveChanges → нет domain UI-события
FE инициатор: loadChats() / ChatChanges.notify() → GET списка
Остальные: видят изменение после F5 или повторного expand+GET
```

### События

```text
ServiceChat.CreateAsync
  CreateStageAsync
    Chats.Create
    Publish(ChatCreated)              // 0022 Participant, до Save
  await SaveChangesAsync()
  await Publish(ChatChanged Created)  // realtime UI

ServiceChat.UpdateAsync / DeleteAsync
  …
  await SaveChangesAsync()
  await Publish(ChatChanged Updated|Deleted)

ServiceRoom.CreateAsync (авточат)
  Publish(RoomCreated) → Chat.CreateStage → ChatCreated
  SaveChanges
  Publish(RoomChanged Created)        // только комната; ChatChanged нет
```

### Realtime

- `IChatConnection.SendToAllAsync` → `Clients.All`
- Клиентский метод `chatChanged`
- Отличие от `chatListUpdated`: тот — user-targeted превью/unread существующей строки; этот — структура списка (add/rename/remove)

### Frontend

- `ChatHub`: `connection.on('chatChanged')` → `chatChanged$`
- `RoomChats`: подписка; created / updated / deleted — патч `chats` (+ сортировка при необходимости)
- Create/rename/delete чата у инициатора: не вызывать полный `loadChats` / `ChatChanges.notify` ради CRUD (оставить `ChatChanges` для join/leave/ролей/удаления комнаты, если ещё нужно)
- Авточат: без изменений UX (expand → GET)
