**Описание:**

Настоящий вход вместо временного выбора пользователя без пароля из [task-0010](task-0010.md): регистрация, вход по логину и паролю, выход. Текущий пользователь определяется по проверенному JWT, а не по заголовку `X-User-Id`. Учётные записи выносятся в отдельную область `Security` по образцу проекта «Автокласс Отчёты».

**Функциональные требования:**

1. Регистрация: на экране входа — переход к регистрации по логину, имени и паролю; после регистрации пользователь сразу вошёл — макет в [Экран входа](#экран-входа).
2. Вход: логин, пароль и галочка «Запомнить меня» — с ней сессия живёт 14 дней, без неё — до закрытия браузера; при ошибке — общий текст «Неверный логин или пароль», без подсказки, существует ли логин.
3. Без входа: виден только экран входа и регистрации; любой другой адрес ведёт на вход, после входа — обратно на запрошенный адрес.
4. Профиль: внизу боковой панели вместо выбора пользователя из списка (task-0010) — имя текущего пользователя, правка своего имени и кнопка «Выйти».
5. Выход: «Выйти» завершает сессию на этом устройстве и открывает экран входа.
6. Пароль: от 8 до 128 символов, без требований к цифрам, регистру и спецсимволам.
7. Пользователи: CRUD `User` из task-0010 сохраняется полностью; создание пользователя — это регистрация и доступно без входа, остальные действия — только после входа; список и просмотр — любому вошедшему, изменить и удалить пользователя может только он сам; после удаления своей учётной записи пользователь выходит на всех устройствах.
8. Существующие пользователи: созданные без пароля (`ivan`, `varia`) удаляются вместе с их участием в чатах и сообщениями; комнаты остаются.

**Технические требования:**

1. Область `Security`: проекты `Datasource.Security.Ef`, `Repositories.Security.Ef`, `Services.Security`, `Services.Security.Tokens`, `Services.Security.Passwords` в `src/backend/SociumApp/Security/`; БД та же — `Socium`, свой контекст `DbContextSecurity` и таблица истории `__EFMigrationsHistory_Security`, как в эталоне — детали в [Эталон «Автокласс Отчёты»](#эталон-автокласс-отчёты).
2. Перенос `User`: модель, конфигурация, репозиторий, сервис, валидаторы, нормализатор, маппер, тексты и тесты переезжают из области Socium в `Security`; в `User` добавляется `PasswordHash` — состав в [Модели](#модели).
3. Миграции: `Task0011` в Socium удаляет таблицу `Users` и внешние ключи на неё; `Task0011` в `Security` создаёт `Users` и `RefreshTokens`. Данные не переносятся — старые пользователи удаляются до миграций (ФТ8).
4. Связь областей: у `Participant`, `Sender` и `Recipient` остаётся `UserId` без навигации и внешнего ключа; проекты Socium не ссылаются на `Security`. Имена и проверку пользователя Socium получает через порт `IUserPort` в `Services.Socium/Ports/` (один запрос на набор `Id`), адаптер в `WebApi/Ports/` вызывает сервис `Security`; не найденный или удалённый пользователь в ленте и списке — «Удалённый пользователь».
5. Текущий пользователь: `CurrentUserFromClaims` (claim `sub`) заменяет `CurrentUserFromHeader`; существование и флаг удаления сервисы Socium проверяют через порт — удалённый пользователь получает `401` сразу, а не после истечения токена.
6. Access-токен: JWT (HS256) на 15 минут, `MapInboundClaims = false`, допуск часов — 1 минута; настройки — секция `Security:Jwt` с классом `JwtOptions`; ключ подписи не короче 32 байт — из `dotnet user-secrets` или переменной окружения, в репозитории его нет; при пустом ключе или заглушке приложение не запускается.
7. Refresh-токен: 64 случайных байта, в БД — только хеш SHA-256; cookie `HttpOnly`, `Secure`, `SameSite=Strict`, путь `/api/account`; при каждом обновлении старый токен отзывается и выдаётся новый; предъявлен уже отозванный — отзываются все токены пользователя — детали в [Поток токенов](#поток-токенов).
8. Пароли: `IPasswordHasher` — обёртка над `PasswordHasher` из ASP.NET Core (PBKDF2); хранится только хеш.
9. Время: истечение токенов считается через `TimeProvider`, а не `DateTimeOffset.UtcNow`.
10. Доступ: все эндпоинты требуют входа, кроме создания пользователя, входа, обновления и выхода; на вход и создание пользователя — ограничение частоты запросов по IP (встроенный `RateLimiter`).
11. Эндпоинты: `api/account` — вход (`POST login`), обновление (`POST refresh`), выход (`POST logout`), текущий пользователь (`GET profile`), правка своего имени (`PUT profile`); `api/user` — CRUD по [rule-0003](../rules/rule-0003-backend.md) п. 37: страницы и действия изменения и удаления чужого пользователя — `403`, удаление своей учётной записи в том же `SaveChangesAsync` отзывает все её refresh-токены. Неверный логин или пароль и недействительный refresh-токен — `401`.
12. Исключения к rule-0003 (согласовать и внести): `api/account` — не CRUD (п. 37); cookie refresh-токена ставит и удаляет контроллер, `refresh` и `logout` берут токен из cookie, а не из параметра запроса (п. 35); `Security` берёт строку `ConnectionStrings:Socium` (п. 39); новый пункт о портах — интерфейс в `Services.{Area}/Ports/`, адаптер в `WebApi/Ports/`.
13. Фронтенд: сервис `Auth` хранит access-токен только в памяти (сигнал); перехватчик добавляет `Authorization: Bearer …` и на `401` один раз обновляет токен (одно обновление на все параллельные запросы) и повторяет запрос; при старте — тихое обновление; guard маршрутов; экран входа и регистрации; `UserPicker`, перехватчик `X-User-Id` и ключ `socium.currentUserId` удаляются.
14. Тесты: по [rule-0004](../rules/rule-0004-tests.md) — фикстуры сервисов и API работают от пользователя по умолчанию через вход, ключ подписи генерируется на запуск; E2E — браузер получает refresh-cookie в начальном состоянии и сам обновляет токен; unit — токены, пароли, валидаторы; интеграционные — вход, ротация, повторное использование, выход, порт.

### Модели

```csharp
// Datasource.Security.Ef
public class User
{
    public required Guid Id { get; set; }

    public required string Login { get; set; }
    public required string Name { get; set; }
    public required string PasswordHash { get; set; }
    public bool IsDeleted { get; set; }

    public virtual ICollection<RefreshToken> RefreshTokens { get; set; } = [];
}

public class RefreshToken
{
    public required Guid Id { get; set; }
    public required Guid UserId { get; set; }

    public required string TokenHash { get; set; }
    public required bool IsPersistent { get; set; }
    public required DateTime CreatedAt { get; set; }
    public required DateTime ExpiresAt { get; set; }
    public DateTime? RevokedAt { get; set; }
    public Guid? ReplacedByTokenId { get; set; }

    public virtual User User { get; set; } = null!;
}
```

В Socium у `Participant`, `Sender` и `Recipient` убираются навигации `User`; поле `UserId` остаётся.

| Поле                | Смысл                                                                                  |
|---------------------|----------------------------------------------------------------------------------------|
| `TokenHash`         | SHA-256 от refresh-токена; сам токен есть только в cookie                              |
| `IsPersistent`      | «Запомнить меня»: при ротации новая cookie получает тот же срок жизни                  |
| `RevokedAt`         | Время отзыва — при ротации, выходе или обнаружении повторного использования            |
| `ReplacedByTokenId` | Токен, выданный взамен при ротации; по нему видно, что предъявлен уже использованный  |

### Поток токенов

| Шаг                 | Что происходит                                                                                                   |
|---------------------|------------------------------------------------------------------------------------------------------------------|
| Вход, регистрация   | Ответ — access-токен и данные пользователя; refresh-токен — в cookie                                             |
| Запрос к API        | Заголовок `Authorization: Bearer …`                                                                              |
| Ответ `401`         | Фронтенд один раз вызывает `POST /api/account/refresh` и повторяет запрос; снова `401` — экран входа             |
| Перезагрузка        | Access-токен из памяти пропал — при старте тихий `refresh`; `401` — экран входа                                  |
| Обновление          | Старый refresh-токен отзывается, выдаётся новый с тем же `IsPersistent`                                          |
| Повторное использование | Предъявлен отозванный токен — отзываются все токены пользователя, ответ `401`                                |
| Выход               | Refresh-токен отзывается в БД, cookie удаляется; фронтенд забывает access-токен                                  |

### Экран входа

```text
┌──────────────────────────────┐
│            Socium            │
│                              │
│  Логин   [________________]  │
│  Пароль  [________________]  │
│  [x] Запомнить меня          │
│                              │
│           [ Войти ]          │
│                              │
│   Нет аккаунта? Регистрация  │
└──────────────────────────────┘
```

Регистрация — та же карточка с полями «Логин», «Имя», «Пароль», кнопкой «Зарегистрироваться» и ссылкой «Уже есть аккаунт? Войти».

### Эталон «Автокласс Отчёты»

Образец — `autoclass-reports.ru/src/backend/ReportsApp/Security`.

Берётся:

- раскладка области `Security` и отдельные проекты `Services.Security.Tokens` и `Services.Security.Passwords`;
- `JwtOptions` с проверкой ключа при старте, `JwtTokenIssuer`, `TokenContext`, `IPasswordHasher`;
- `RefreshToken` с хешем и временем отзыва, ротация при обновлении;
- регистрация `JwtBearer` в `WebApi/Middleware/AuthenticationRegistration.cs`;
- одна БД с отдельной историей миграций `__EFMigrationsHistory_Security`;
- порт `IServiceUserPort` в основной области и адаптер `ServiceUserPort` в `WebApi/Ports/`.

Отличается:

| Эталон                                              | Socium                                                              |
|-----------------------------------------------------|---------------------------------------------------------------------|
| Refresh-токен в теле запроса и в `localStorage`     | В `HttpOnly`-cookie, JavaScript его не видит                        |
| Отозванный токен просто недействителен              | Повторное использование отзывает все токены пользователя            |
| Access-токен — 600 минут                            | 15 минут                                                            |
| `DateTimeOffset.UtcNow`                             | `TimeProvider`                                                      |
| Недействительный refresh-токен — `422`              | `401`                                                               |
| Пароль: заглавная, строчная, цифра, спецсимвол      | Только длина 8–128                                                  |
| Порт отдаёт имя по одному `Id`, вместо имени — `Id` | Набор `Id` одним запросом; вместо имени — «Удалённый пользователь» |
| Нет ограничения частоты входа                       | `RateLimiter` на вход и создание пользователя                       |
| Подтверждение почты, сброс пароля, роли             | Не входят в задачу                                                  |

### Решения без разработчика

Задача выполнялась без разработчика; вопросы, которые возникли по ходу, решены так:

| Вопрос | Решение |
|--------|---------|
| Где лежит `ICurrentUser`, если он нужен Socium и Security | В `Services.Shared/Api/`; исключение 2 rule-0003 дополнено |
| Как зарегистрироваться через CRUD `User` и сразу войти | Фронтенд вызывает `POST api/user`, затем `POST api/account/login` тем же паролем |
| Как отдать refresh-токен контроллеру, не показав его в JSON | Поля `RefreshToken`, `RefreshTokenExpiresAt`, `IsPersistent` в `AccountTokenResponse` с `[JsonIgnore]` и без `required` (иначе System.Text.Json не сериализует модель); cookie ставит контроллер |
| Нужен ли вход для списка и просмотра пользователей `Security` | Да, без входа — `401`; изменить и удалить — только себя (`403`); удаление себя отзывает все токены |
| Что делает порт при сбое `Security` | Бросает исключение — сервис Socium отвечает `500`; «не найден» — `null`, на экране «Удалённый пользователь» |
| Сортировка участников без навигации `User` | По имени в памяти после ответа порта |
| Формат `401` от JwtBearer | Problem Details «Требуется вход в систему.», как у остальных ошибок |
| Лимит частоты | Настраивается (`Security:RateLimit`), в тестах поднят, тест `429` снижает его |
| Срок refresh-токена | Скользящие 14 дней: каждый `refresh` выдаёт новый токен на полный срок; без периода прощения |
| Порядок миграций | Socium, затем Security — в `Program` и `TestDatabase` |
| Что делать с чатами, где не осталось участников после очистки | Скрипт удаляет их; перед запуском снят `pg_dump` |
| Ключ подписи в тестах | Новый случайный на каждый запуск фикстуры; клиент API входит по-настоящему; базовый адрес `https`, чтобы cookie `Secure` отправлялась |
| Ключ локально | `UserSecretsId` в WebApi, `start-solution.ps1` создаёт ключ сам |
| «Запомнить меня» при регистрации | Галочка есть и на регистрации — регистрация сразу выполняет вход |
| Маршрутизация | `/login` под `guestGuard`, остальное — в `Shell` под `authGuard` |
| Сервис `CurrentUser` | Оставлен фасадом над `Auth`, чтобы экраны чатов не зависели от устройства входа |
| `UserApi.getList` и модели списка | Удалены — после ухода `UserPicker` не используются |
| Как E2E получает сессию | Страница того же адреса вызывает `fetch('/api/account/login')`, браузер сам хранит cookie |
| Срок access-токена в E2E | 240 минут — HTTP-клиенты фикстуры токен не обновляют |
| Открытый редирект через `returnUrl` | `safeReturnUrl` пропускает только пути приложения (`/…`, не `//…` и не `/login`) |
| Тема на экране входа | Переключатель темы в правом верхнем углу |
| Имя после правки своего профиля | Лента и панель участников перечитываются сразу, без перезагрузки |

### Известные ограничения

- Комнаты не проверяют пользователя через порт: токен удалённого пользователя работает для комнат до истечения (до 15 минут); чаты, сообщения и участники отвечают `401` сразу.
- Время ответа входа для несуществующего логина короче (хеш пароля не проверяется) — по времени можно отличить существующий логин.
- Нет периода прощения при обновлении: две вкладки, одновременно обновившие токен, или оборванный ответ `refresh` приводят к выходу на всех устройствах.
- Сброса пароля, подтверждения почты и ролей нет — вне задачи.
