**Описание:**

Добавить пользователя, к сообщениям — отправителя и получателей, а к чатам — участников: сущности `User`, `Sender`, `Recipient` и `Participant` в БД Socium, чтобы по модели было сразу видно, кто состоит в чате, кто написал сообщение и кому оно адресовано. Задача фиксирует согласованные названия и состав моделей; статусы доставки и прочтения в неё не входят.

**Функциональные требования:**

1. Отправитель: у каждого сообщения ровно один отправитель — пользователь, который его написал; залогинившийся пользователь, когда пишет, всегда отправитель — состав в [Модели](#модели).
2. Получатели: у сообщения может быть много получателей — пользователи, которым оно адресовано в чате — состав в [Модели](#модели).
3. Сообщение: остаётся в своём чате (связь «один чат — много сообщений» из task-0008), текст и время создания не меняются — состав в [Модели](#модели).
4. Участники: участие в чате даёт пользователю право отправлять и получать сообщения в нём; у чата может быть много участников, пользователь состоит в чате один раз; получатели сообщения — остальные участники чата на момент отправки — состав в [Модели](#модели).
5. Чаты пользователя: по участию видно, в каких чатах состоит пользователь; в панели по-прежнему показываются все комнаты и все чаты.
6. Вступление в чат: создатель чата автоматически становится его участником; приглашения и вступление по желанию — отдельной задачей.
7. Чат без участия: пользователь, который не участник, открывает чат и не видит сообщений и поля ввода — по центру окна текст «Вы не участник этого чата» и кнопка «Вступить в чат»; кнопка пока без логики, вступление — отдельной задачей — макет в [Окно чата без участия](#окно-чата-без-участия).
8. Существующие данные: чаты и сообщения, созданные до задачи, удаляются (у них нет участников и отправителей); комнаты остаются.
9. Пользователь: `User` — тот, кто залогинился; пользователь не удаляется физически, а помечается флагом «удалён» — его сообщения и участие в чатах сохраняются.
10. Текущий пользователь: настоящего входа пока нет — в шапке выбор пользователя из списка без пароля и добавление нового по логину и имени; выбор запоминается между перезагрузками; настоящий вход — отдельной задачей — детали в [Временный текущий пользователь](#временный-текущий-пользователь).

**Технические требования:**

1. Названия: классы `User`, `Sender`, `Recipient`, `Participant`, `Message` и их поля — как согласовано с разработчиком; `Sender` и `Recipient` — отдельные сущности ради прозрачности модели, даже там, где хватило бы поля в `Message` — состав в [Модели](#модели).
2. Оформление: по [rule-0003](../rules/rule-0003-backend.md) — ключи `Guid` v7, обязательные поля `required`, навигации `virtual … = null!`, коллекции `= []`; время — UTC.
3. Время создания: у `Message` остаётся поле `CreatedAt` из task-0008 — переименование в `Created` не требуется.
4. Целостность: уникальные индексы `IX_Users_Login` (логин не повторяется; хранится в нижнем регистре, поэтому `Ivan` и `ivan` — один логин), `IX_Senders_MessageId` (один отправитель на сообщение), `IX_Recipients_MessageId_UserId` (один получатель — один раз) и `IX_Participants_ChatId_UserId` (пользователь в чате — один раз); индекс `IX_Participants_UserId` — для выборки чатов пользователя; удаление сообщения удаляет его `Sender` и `Recipient`, удаление чата — его `Participant`.
5. Доступ: сервис сообщений выдаёт и принимает сообщения только участнику чата; неучастнику — отказ без данных и без записи в БД (скрыть ленту только во фронтенде недостаточно). Сервис чатов при создании чата в той же транзакции добавляет создателя в `Participant` и сообщает фронтенду, участник ли текущий пользователь.
6. Удаление пользователя: мягкое — флаг `User.IsDeleted`, строка в `Users` остаётся; внешние ключи `Sender`, `Recipient` и `Participant` на `Users` — `Restrict`, каскада от пользователя нет.
7. Текущий пользователь: сервисы получают его через абстракцию `ICurrentUser`; временная реализация читает заголовок `X-User-Id`, при настоящем входе меняется только реализация — детали в [Временный текущий пользователь](#временный-текущий-пользователь).
8. Статусы: поля отправки, доставки, прочтения и удаления у получателя в задачу не входят; если появятся — nullable-время (`DateTime?`), а не перечисление.
9. Тесты: по [rule-0004](../rules/rule-0004-tests.md) — unit и интеграционные тесты новых сущностей, изменённого CRUD сообщений и отказа неучастнику.

**План реализации:**

1. Карточка и реестр.
2. `Datasource.Socium.Ef`: модели `User`, `Sender`, `Recipient`, `Participant`, навигации `Message.Sender`, `Message.Recipients` и `Chat.Participants`, конфигурации, миграция `Task0010`.
3. Пользователи: CRUD `User` (список, добавление по логину и имени, мягкое удаление), `ICurrentUser` и временная реализация по заголовку `X-User-Id`.
4. Репозитории и сервис сообщений: проверка участия отправителя, запись отправителя и получателей (по участникам чата) при создании сообщения, выдача в ответах API.
5. Сервис чатов: создатель чата — участник; признак участия текущего пользователя в ответе.
6. Фронтенд: выбор текущего пользователя в шапке, заголовок `X-User-Id` в запросах; окно чата без участия — заглушка с кнопкой «Вступить в чат» вместо ленты и поля ввода.
7. Тесты бекенда, фронтенда и E2E.
8. Очистка существующих чатов и сообщений в локальной БД; комнаты не трогаются.
9. Сборка, прогон тестов, документы.

### Модели

Согласованный состав (поля, которые понадобятся позже, сюда не входят):

```csharp
public class User
{
    public required Guid Id { get; set; }

    public required string Login { get; set; }
    public required string Name { get; set; }
    public bool IsDeleted { get; set; }
}

public class Sender
{
    public required Guid Id { get; set; }

    public required Guid MessageId { get; set; }
    public required Guid UserId { get; set; }

    public virtual Message Message { get; set; } = null!;
    public virtual User User { get; set; } = null!;
}

public class Recipient
{
    public required Guid Id { get; set; }

    public required Guid MessageId { get; set; }
    public Guid? UserId { get; set; }

    public virtual Message Message { get; set; } = null!;
    public virtual User? User { get; set; }
}

public class Participant
{
    public required Guid Id { get; set; }

    public required Guid ChatId { get; set; }
    public required Guid UserId { get; set; }

    public virtual Chat Chat { get; set; } = null!;
    public virtual User User { get; set; } = null!;
}

public class Message
{
    public required Guid Id { get; set; }
    public required Guid ChatId { get; set; }

    public required DateTime CreatedAt { get; set; }
    public required string Text { get; set; }

    public virtual Chat Chat { get; set; } = null!;
    public virtual Sender Sender { get; set; } = null!;
    public virtual ICollection<Recipient> Recipients { get; set; } = [];
}
```

В `Chat` из task-0006 добавляется коллекция участников:

```csharp
public virtual ICollection<Participant> Participants { get; set; } = [];
```

| Термин       | Смысл                                                                                   |
|--------------|-----------------------------------------------------------------------------------------|
| `User`       | Пользователь — тот, кто залогинился; уникальный `Login`; при удалении помечается флагом `IsDeleted` |
| `Message`    | Сообщение в чате: текст и время создания                                                |
| `Sender`     | Отправитель сообщения — ровно один на сообщение                                         |
| `Recipient`  | Получатель сообщения — может быть много; позже сюда лягут статусы для каждого человека |
| `Participant` | Участник чата: может отправлять и получать в нём сообщения; показывает, в каких чатах состоит пользователь; по участникам создаются строки `Recipient` при отправке |

### Окно чата без участия

Заголовок чата остаётся, лента и поле ввода не показываются. Заглушка по центру области сообщений — тот же приём, что у пустой ленты «Сообщений пока нет»:

```text
┌──────────────────────────────────────────┐
│ Обсуждение 1                             │
├──────────────────────────────────────────┤
│                                          │
│         Вы не участник этого чата        │
│            [ Вступить в чат ]            │
│                                          │
└──────────────────────────────────────────┘
```

Кнопка внизу, на месте поля ввода (как в Telegram), подходит, когда сообщения видны и их можно читать до вступления. Здесь тексты скрыты, область сообщений пустая — поэтому заглушка по центру.

### Временный текущий пользователь

Входа и авторизации в проекте нет; по решению разработчика в этой задаче — временный выбор текущего пользователя без пароля.

| Часть      | Решение                                                                                                                  |
|------------|--------------------------------------------------------------------------------------------------------------------------|
| Шапка      | Выпадающий список пользователей (кроме удалённых) и «Добавить» по логину и имени; без выбранного пользователя писать нельзя |
| Хранение   | Выбранный `Id` — в `localStorage` под ключом `socium.currentUserId` ([rule-0005](../rules/rule-0005-frontend.md))       |
| Запросы    | Фронтенд добавляет заголовок `X-User-Id` ко всем запросам API                                                            |
| Бекенд     | `ICurrentUser` в `Services.Socium`; временная реализация в `WebApi` читает `X-User-Id`; нет заголовка или пользователь удалён — отказ |
| Поля `User`| `Id`, `Login` (уникальный), `Name` (подпись в ленте и списке), `IsDeleted`; хеш пароля и прочее — в задаче настоящего входа |
| Замена     | Настоящий вход заменяет реализацию `ICurrentUser` и выбор в шапке; сервисы и модели не меняются                          |
