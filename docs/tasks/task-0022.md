**Описание:**

Рефакторинг создания чата: участник-создатель с ролями `ChatAdmin` + `ChatParticipant` создаётся не внутри `ServiceChat.CreateStageAsync`, а реакцией на domain event `ChatCreated` (тонкий handler → `IServiceParticipant` Stage), по тому же принципу, что авточат и `RoomAdmin` на `RoomCreated` ([task-0019](task-0019.md), [task-0021](task-0021.md)). Полный обзор **всех** методов всех сервисов SociumApp (не только Create, не только Participant) — [Инвентаризация сервисов](#инвентаризация-сервисов); в объём 0022 попадает один антипаттерн, остальные кандидаты — отдельные задачи или leave as-is.

**Функциональные требования:**

1. Поведение: после создания чата (вручную или авточат комнаты) создатель — участник с `ChatAdmin` и `ChatParticipant`; для UI это по-прежнему бейдж админа / `can*` — без смены контрактов API — [Целевая цепочка](#целевая-цепочка).
2. Атомарность: чат, участие и назначения ролей либо все в одной транзакции внешнего `SaveChanges`, либо ничего — [Целевая цепочка](#целевая-цепочка).
3. Join: обычное вступление в чат (`ServiceParticipant.CreateAsync`) использует тот же Stage, без дублирования записи Participant/ролей — [Целевая цепочка](#целевая-цепочка).

**Технические требования:**

1. Эталон: `ServiceRoom.CreateAsync` пишет только Room → `Publish(RoomCreated)` → Stage-handlers → один `SaveChanges` (rule-0003 п. 26, 44–45; [AGENTS.md](../../AGENTS.md)) — [Эталон Room](#эталон-room).
2. Событие: `ChatCreatedEvent` + handlers в `Services.Socium/Events/ChatCreatedEvent.cs` — [AGENTS.md](../../AGENTS.md).
3. Chat Stage: `CreateStageAsync` пишет **только** Chat, затем `Publish(ChatCreated)`; без `SaveChanges` — [Целевая цепочка](#целевая-цепочка).
4. Participant Stage: `CreateStageAsync` (новый) — Participant + `ChatParticipant`; при bootstrap создателя чата — ещё `ChatAdmin` (пара ролей в одной Stage, инвариант [task-0021](task-0021.md)); HTTP `CreateAsync` вызывает Stage и сам делает `SaveChanges` + notify — [Целевая цепочка](#целевая-цепочка).
5. Роли: не выносить в отдельное событие «назначения» — живут в Participant Stage (как `AssignRoomAdminStage` живёт у Room) — [Инвентаризация сервисов](#инвентаризация-сервисов).
6. Тесты: create чата / авточат комнаты / join; откат при ошибке handler; регрессия list/info `IsAdmin` / `can*`.

**Дополнительные сведения:**

### Критерий «кандидат в Events»

Считать похожим на 0022 (и писать в карточку), если метод сервиса A **до/в одном UoW** создаёт / обновляет / удаляет сущность **другого агрегата** (не owned-часть своего, не свой сценарий ролей участника), вместо `Publish` → Stage чужого `IService*`.

Не кандидаты: Display*/List/Info (read); owned children (`Message.Sender`/`Recipients`); свои RoleAssignment в Stage того же concern (`AssignRoomAdminStage`, grant/revoke admin у Participant); ports после `SaveChanges` (email, notify, attach); каскад БД.

### Инвентаризация сервисов

Обзор по сервисам (сводка). Детализация по методам — ниже.

| Area / сервис | Антипаттерн «чужой агрегат inline»? | Уже Events? | В объём 0022? |
|---------------|-------------------------------------|-------------|---------------|
| `ServiceRoom` | Нет | Да: `RoomCreated` / `RoomChanged` | Эталон |
| `ServiceChat` | **Да** — `CreateStageAsync` → Participant + ChatRoleAssignments | Нет | **Да** |
| `ServiceParticipant` | Нет (свои Participant + роли); нужен Stage для handler | Нет | **Да — Stage** |
| `ServiceMessage` | Нет (owned + ports) | Нет | Нет |
| `ServiceUser` | Soft-delete → revoke RefreshTokens (Security, не Socium) | Нет | Нет (опц. отдельно) |
| `ServiceAccount` | RefreshToken / User — свой сценарий Account | Нет | Нет |
| `ServiceAppRole` | Только read | — | Нет |
| `ServiceEmailToken` | Своя сущность Messaging | — | Нет |
| `ServiceStoredFile` | Своя сущность Files | — | Нет |
| `ServiceChatNotify` | Sink SignalR | `RoomChanged` → notify | Нет ([task-0025](task-0025.md) для Chat) |

**Вывод:** единственный антипаттерн уровня 0022 («сервис A пишет чужой агрегат inline до Save») — `ServiceChat.CreateStageAsync` (Participant + роли). ### Эталон Room

```text
ServiceRoom.CreateAsync
  Rooms.Create
  Publish(RoomCreated)          ← до SaveChanges
    → AssignRoomAdminStage      (RoomAdmin)
    → Chat.CreateStageAsync     (сейчас ещё и Participant+роли — уйдёт в 0022)
  SaveChanges
  Publish(RoomChanged)          ← после SaveChanges (realtime)
```

### Целевая цепочка

```text
ServiceChat.CreateStageAsync / CreateAsync path
  Chats.Create only
  Publish(ChatCreated)          ← до внешнего SaveChanges
    → Participant.CreateStageAsync(creator, AssignChatAdmin: true)
         Participant + ChatParticipant + ChatAdmin
  SaveChanges у издателя (Chat.Create или Room.Create через авточат)

ServiceParticipant.CreateAsync (join)
  CreateStageAsync(currentUser, AssignChatAdmin: adminCount == 0)
  SaveChanges
  notify joined
```

Роли чата **не** получают отдельного события: инвариант пары `ChatAdmin`+`ChatParticipant` и join остаются в одном Stage участника.

Ручной чат и авточат (`CreateDefaultChatOnRoomCreatedHandler` → `Chat.CreateStageAsync`) получают участника только через `ChatCreated`.
